# GB10 content and vision benchmark suite

The text and vision suites have separate fixtures, gates and reports. A text
speed result is not proof that Vision-Exp serves images correctly. The current
vision candidate failed its text non-regression gate; see [vision.md](vision.md).

## Text protocol

Eight fixed synthetic prompts cover technical explanation, English prose,
Python, TypeScript, mathematics with visible working, Spanish, Chinese and JSON
generation. The explanation prompt is copied verbatim from the
[Anemll GB10 reference](https://github.com/Anemll/dspark-vllm-gx10#performance).
The reference publishes best-of-trial aggregate throughput; this suite primarily
reports medians and ranges. Different checkpoints or statistics are not a
matched speedup comparison.

Default matrix: C1/C2/C4, three measured trials per setting, 512 output tokens,
128-token excluded warmup per content/concurrency, temperature0, thinking off,
seed5205. That is168 measured requests plus56 warmup requests. Each category has
one fixed prompt: repeated timing coverage, not broad content/quality sampling.
Other than the reference prompt, early deterministic case IDs distinguish
warmup, trial and request inputs. All exact bodies, hashes, usage and SSE events
are retained. These are short natural-content prompts, not equal-input-length
prefill tests; prompt-token counts are reported rather than assumed equal.

```sh
python3 benchmarks/benchmark_content.py \
  --base-url http://spark-head.local:8888 --model MODEL_ID \
  --concurrency 1,2,4 --trials 3 --max-tokens 512 --warmup-tokens 128 \
  --seed 5205 --timeout 90 --budget-seconds 1800 \
  --provenance CONTROL_PROVENANCE.json \
  --output .local/results/content-control.json
```

Use a new output path. `--plan-only` saves example requests without network
access. `--cases python-code,typescript-code` selects a subset; a new
`--fixture` can provide additional prompts, local PNG/JPEG images and strict
known-answer JSON checks. Benchmark messages do not execute generated code.
Fixed-length JSON output may be truncated and is not scored as valid JSON.
Math is visible explanation with thinking disabled, not a reasoning-on eval.

## Metrics and integrity

| Metric | Meaning |
|---|---|
| Aggregate output tok/s | Validated output tokens divided by the wave's first-submit to last-completed-HTTP-stream interval; includes input processing, queueing and transport. |
| Server decode tok/s/request | `(output tokens − completed requests) / sum(request_decode_seconds)` from isolated server counters. At C>1 this is a token-weighted per-request rate, not aggregate throughput. |
| Client decode proxy | `(completion tokens − 1) / time between first and last meaningful SSE delta`; speculative chunks prevent true per-token timing. |
| TTFT | Submission to first nonempty content/reasoning/tool delta. Role metadata does not count. |
| DSpark acceptance | Accepted draft tokens / drafted tokens from server counters; not estimated from chunk counts. |
| Server prefill | Computed input tokens / summed server request-prefill time when counters are available and isolated. |

The pinned vLLM implementation defines request decode time from first to last
engine output event, excluding the token generated by prefill. It includes
preemption delays and is not a kernel-only timing. Final report serialization
is outside aggregate wave timing. Individual request records are saved during
collection; full reports are checkpointed after each wave.

Server metrics require zero queued/running requests before/after each wave,
exact completed-request/output-token deltas, and nondecreasing counters. A
mismatch or request failure stops the suite; it is not averaged into a passing
result. Missing usage, missing DONE, invalid finish or short fixed-length output
also fail. `--metrics off` supports a server without vLLM counters, but explicitly
withholds server timing and acceptance and cannot prove traffic isolation.

Small samples report medians/ranges. They do not establish reliable p95/p99 or
small performance gains. Raw report schemas preserve failed/partial waves.
The transport's socket watchdog bounds streaming; OS connection establishment
still depends on the platform network stack. The whole-suite deadline is checked
at every network operation and clamps per-request budgets.

## Context, agent and correctness lanes

Keep these separate from short-prompt content decoding:

- Exact prefill:1K/2K/4K/8K/16K/32K, plus33,966/36,549/40,720/65,536-token
  boundaries. Use the existing prefill harness and identical saved seeds.
- Agent context: exact8K coding and growing/repeated/divergent history; do not
  label synthetic fixtures as NVIDIA SpeedBench-Coding.
- Protocol correctness: streaming, parsed tool calls, known-answer JSON and
  measured prefix-cache contracts. Speed alone does not establish correctness.

Previously accepted evidence may be reused only with its original date,
checkpoint/configuration and metric definition shown. The September5 content
baseline reuses the existing8c control's September4 prefill/8K coding evidence;
it does not pretend those runs were repeated or measured on Vision-Exp.

## Separate visual benchmark

First generate deterministic fixtures locally. Pillow>=10.1 is the only extra
dependency; the serving client itself uses the standard library. The manifest
records Pillow version, builder source hash and image hashes; font rendering
across library versions is not assumed identical.

```sh
python3 benchmarks/prepare_vision_benchmark.py \
  --output-dir .local/vision-fixtures-v1

# This can run offline now; remove --plan-only only on a verified vision API.
python3 benchmarks/benchmark_content.py --model VISION_MODEL_ID \
  --fixture .local/vision-fixtures-v1/vision-correctness-v1.json \
  --concurrency 1 --trials 1 --max-tokens 128 --budget-seconds 300 \
  --plan-only --output .local/results/vision-correctness-plan.json
```

| Lane | Content | Gate/report |
|---|---|---|
| Correctness | OCR shipment note | Exact tracking code, units, destination |
| Correctness | Bar chart | Largest region and numeric total |
| Correctness | Invoice/document | Invoice ID and amount due |
| Correctness | Spatial layout | Correct colors/shapes/positions |
| Correctness | Two-image comparison | Correct warehouse and stock difference |
| Performance | Each of the five categories at512/1024/2048 pixels square | Separate TTFT,128-token decode, aggregate throughput and acceptance at C1/C2 |

Correctness uses five1024px cases and strict JSON known answers. Every warmup
and measured request must pass before the throughput suite is permitted.
Throughput has15cases, three measured trials per concurrency, plus warmup.
Correctness and throughput images differ in a visible fixture stamp and hash,
so the exact same image was not primed by the correctness suite.

```sh
python3 benchmarks/benchmark_content.py \
  --base-url http://vision-head.local:8888 --model VISION_MODEL_ID \
  --fixture .local/vision-fixtures-v1/vision-throughput-v1.json \
  --concurrency 1,2 --trials 3 --max-tokens 128 --warmup-tokens 128 \
  --timeout 90 --budget-seconds 1200 \
  --provenance VISION_PROVENANCE.json \
  --output .local/results/vision-throughput.json
```

Retain first-touch warmup TTFT separately from subsequent warmed measurements.
The exact image repeats after first touch: warmed image/processor cache is
intended, not independently proven. This does not establish encoder-cold latency.
True cold-image tests need fresh image hashes and no prior processor/encoder
cache entry; do not flush a live cache to manufacture a comparison. Image encoder
GPU time is unavailable from these API metrics and must remain N/A without a
separate, explicitly labelled instrumented run. Pixel dimensions are not image
token counts; preserve processor token/grid evidence before making such claims.

These are synthetic visual probes, not natural-photo recognition, OCRBench,
DocVQA or chart-QA dataset scores. An external image manifest can extend coverage
with licensed photos/screenshots and documented checks. Do not substitute text
descriptions for image bytes, compare different model weights as a text A/B,
or publish vision throughput after a failed visual-content check.

The [Anemll SGLang vision reference](https://github.com/Anemll/SGLang-DSv4F-vision-2xSparks)
is contextual only: its roughly30.5tok/s text and33tok/s image smoke figures use
a different engine/model workload, not this matched matrix. No vLLM-vs-SGLang
gain is inferred from those figures.

## Safety and verification

Record exact image IDs on both ranks, checkpoint/configuration fingerprints,
DSpark method/draft settings, quantization, scheduler/cache/graphs and software
revisions. Use an idle cluster and an exclusive experiment lock, a hard time
budget, before/during/after resource checks, preserved logs and the validated
rollback configuration. No serving image rebuild is needed for client changes.
Stop a failed gate before expanding the workload or diagnosing a candidate.

```sh
python3 -m unittest discover -s tests -p test_content_benchmark.py -v
python3 -m unittest discover -s tests -p test_vision_benchmark_fixtures.py -v
python3 -m compileall -q benchmarks
git diff --check
```
